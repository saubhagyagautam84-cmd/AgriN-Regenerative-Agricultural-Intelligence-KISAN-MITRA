# 🌾 Kisan Sathi — AI Crop & Farming Monitor (Part A)

A farmer enters **4 things** — PIN code, land size, crop, sowing date — and the
system fetches or computes everything else (soil health card, weather, crop
agronomy) and returns four pieces of advice on a dashboard.

**This is Part A: the skeleton.** Every advisory number you see is produced by
a transparent rule-based stub, clearly marked `DEMO DATA` in the UI and
`details.is_dummy_data = true` in the JSON. The point of Part A is the
*contract* — so real ML models can be dropped in one at a time without
touching the frontend.

## Quick start

Two terminals. Backend first.

### Terminal 1 — FastAPI backend

```powershell
cd agri-monitor\backend

# first time only
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# every time
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --port 8001
```

Check it: <http://127.0.0.1:8001/docs> (interactive Swagger UI)

> **Why port 8001 and not 8000?** Port 8000 was already occupied on the machine
> this was built on. If 8000 is free for you, use it — just change
> `NEXT_PUBLIC_API_BASE_URL` in `frontend/.env.local` to match.

### Terminal 2 — Next.js frontend

```powershell
cd agri-monitor\frontend

# first time only
copy .env.local.example .env.local
npm install

# every time
npm run dev
```

Open <http://localhost:3000> and press **▶ Load demo farm**, or fill the form
(try PIN `141001` + Wheat, or `462001` + Soybean).

> ⚠️ **Node.js is required and was not installed on the build machine.**
> `C:\Program Files\nodejs` had `npm.cmd` but no `node.exe` — a broken install.
> Fix with `winget install OpenJS.NodeJS.LTS`, restart your terminal, then
> confirm with `node --version`. The frontend has therefore **not been run
> yet** — see [Status](#status) below.

### Terminal 3 — CNN crop-health check (optional, Part B)

The trained model files (`crop_health_model.h5`/`.tflite`) travel with the
repo via **Git LFS** - `git lfs pull` after cloning fetches them like any
other file. What does **not** travel with the repo: the isolated Python
3.11 + TensorFlow venv that runs them, and the PlantVillage training data -
both are gitignored and live outside OneDrive/cloud-sync at
`~/dev/kisan-sathi-training/` (junctioned back into `backend/cnn_training/`
so the code's relative paths work unchanged - see `backend/cnn_training/`'s
`.venv`, `PlantVillage-Dataset/`, `subset_small/`).

```powershell
# first time only - recreates the inference venv (TensorFlow has no wheel
# for very new Python versions yet, hence the separate 3.11 install)
winget install Python.Python.3.11
cd agri-monitor\backend\cnn_training
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install tensorflow==2.15.0 numpy
```

Without this venv, `/api/crop-health-check` still works - it gracefully
falls back to the baseline placeholder (`is_placeholder: true`) rather than

## The one contract that matters

Every module endpoint returns **exactly this envelope** — that is the whole
architecture:

```jsonc
{
  "module_name": "irrigation_advice",
  "status": "ok",              // "ok" | "partial" | "error"
  "summary": "Irrigate in about 2 days - roughly 34 mm (1,38,000 litres for your field).",
  "details": { /* module-specific, free-form */ },
  "confidence": null,          // null for rule-based; a real number for ML
  "timestamp": "2026-09-10T17:01:59Z"
}
```

Defined once in each language and kept in sync by hand:

- Python — `backend/models/schemas.py` → `ModuleResponse`
- TypeScript — `frontend/lib/types.ts` → `ModuleResponse`

Because every module returns the same shape, `ModuleCard.tsx` renders **all**
of them, and a fifth module needs zero frontend work.

## How to swap dummy logic for a real model

This is the part Part A exists for. To replace, say, crop recommendation:

1. Open `backend/services/modules/crop_recommendation.py`.
2. Replace the body of `run(aggregated: AggregatedData) -> ModuleResponse`.
   Read whatever you need off `aggregated` — it already holds soil, weather,
   crop reference, land size and crop stage.
3. Return a `ModuleResponse` with the same `module_name` and the same
   `details` keys listed in the module's docstring. Add new keys freely.
4. Set a real `confidence` and delete the `DUMMY_CONFIDENCE` constant.
5. Set `details.is_dummy_data = False` — the `DEMO DATA` badge disappears on
   its own.

**Nothing in `frontend/` changes.** Run `smoke_test.py`, then the UI.

To add a **fifth** module: create `services/modules/pest_risk.py` with a
`run()` function, add it to `MODULE_RUNNERS` and `MODULE_ORDER` in
`services/modules/__init__.py`, and add a route in `main.py`. It will render
on the dashboard immediately (as a JSON dump until you write a view for it in
`ModuleDetails.tsx`).

Search the codebase for `TODO(ML)`, `TODO(integration)` and `TODO(agronomy)` —
every swap point is marked.

## Seed data

All three files under `backend/data/` are **hand-compiled placeholders**.

**`crop_reference.json`** — 10 crops (wheat, rice, maize, cotton, sugarcane,
soybean, mustard, chickpea, groundnut, pearl millet) with NPK requirements,
water requirement, ideal pH band, rotation compatible/avoid lists, growth
duration and critical irrigation stages. Values are from ICAR package-of-
practice guidance and **must be verified by an agronomist** before any real
use. Add the remaining crops by copying an existing block.

**`soil_health_card.csv`** — 20 rows across Punjab, MP, Maharashtra, UP, Bihar,
Karnataka, TN and Rajasthan. Schema: `sample_id, state, district, block,
village, pincode, soil_type, test_date, N_kg_per_ha, P_kg_per_ha, K_kg_per_ha,
pH, EC_dS_per_m, organic_carbon_pct, S_ppm, Zn_ppm, Fe_ppm, Cu_ppm, Mn_ppm,
B_ppm`.

> **Two rows are intentionally broken** so you can watch the loader handle bad
> data — this is a feature, not a bug:
> - `SHC-XX-000000-001` has no location → **rejected** with a reason
> - `SHC-RJ-302001-001` has an extra field → **skipped by the CSV parser**
>
> Both are reported at `GET /api/health/data`. A third row
> (`SHC-TN-641001-002`) has `NA` for pH and P — those cells coerce to `null`
> and the row is **kept**. Delete all three once you trust the loader.

**Lookup degrades gracefully**: exact PIN code → district average → state
average → nothing. `soil.match_level` records which happened, and modules drop
to `status: "partial"` for anything but an exact match, so the farmer is told
when advice is based on a neighbour's soil rather than their own.

## Known limitations (be honest in the demo)

- **Weather is synthetic.** `services/weather.py` generates numbers from a
  month-of-year climatology, seeded by PIN code so a given farm looks the same
  all day. No network call is made. Swap for Open-Meteo (free, no API key).
- **15 PIN codes only.** Anything else falls back to "location not resolved"
  and the advice goes generic — deliberately visible in the UI.
- **All advice is rule-based**, using published rating bands and simple water
  balance. No model has been trained.
- **Bigha is assumed to be 0.2529 ha** (UP/Bihar). It varies by state; a
  warning is attached to the response.
- **No database, no auth, no persistence.** Nothing is stored between requests.
- **Tracebacks are returned in module error responses** — useful now, strip
  before any public deployment.
